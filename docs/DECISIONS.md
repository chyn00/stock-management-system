# 설계 결정 기록

## 2026-11-21 — JUnit 5와 Spring Boot 4.1의 통합 테스트

- **결정:** JUnit 5.14.4를 유지하며, PostgreSQL 통합 테스트에서 Spring 애플리케이션을 직접 시작하고 종료한다.
- **배경 및 문제:** Spring Boot 4.1.3의 Spring Framework 7 확장은 JUnit 6 이상을 요구한다. JUnit 5로 고정한 `@SpringBootTest` 실행에서 `NoSuchMethodError`가 발생했다.
- **고려한 대안:** JUnit 6으로 변경한다. Spring Boot 버전을 낮춘다.
- **선택 이유:** 사용자가 선택한 Java 21, Spring Boot 4.1.3, JUnit 5를 유지하며 실제 애플리케이션과 PostgreSQL을 검증한다.
- **단점 및 한계:** SpringExtension의 컨텍스트 캐시와 테스트 인스턴스 자동 주입을 사용하지 못한다. 컨텍스트 종료와 테스트 데이터 정리를 명시적으로 관리해야 한다.
- **재검토 조건:** 테스트 실행 시간이나 유지보수 부담으로 JUnit 버전 변경을 검토할 때.

## 2026-11-21 — 초기 재고를 집계 테이블과 movement로 관리

- **결정:** 상품 메타데이터(`products`), 현재 재고(`stocks`), 변동 이력(`stock_movements`)을 분리한다. 재고 변경은 `stocks` 조건부 UPDATE와 movement INSERT를 같은 PostgreSQL 트랜잭션에서 수행한다.
- **배경 및 문제:** 현재 수량은 빠르게 조회해야 하며, 그 수량이 바뀐 근거도 추적할 수 있어야 한다. movement 기간별 SUM은 데이터 증가에 따라 비용이 커질 수 있다.
- **고려한 대안:** movements만 조회해 현재고를 매번 계산하거나, 현재고만 저장해 변경 이력을 남기지 않는다.
- **선택 이유:** 집계 테이블로 현재고 조회와 음수 방어를 단순화하고 append-only movements로 변경 근거를 보존한다. 요청마다 movement 합계를 다시 계산하지 않고, 커밋 시 집계와 movement 합계가 맞도록 한 트랜잭션에서 갱신한다.
- **단점 및 한계:** 두 표현을 함께 갱신하고 정합성을 테스트해야 한다. 조건부 UPDATE는 같은 재고 행을 바꾸는 요청을 DB 내부에서 직렬화한다.
- **재검토 조건:** 실제 성능 측정이나 요구가 단일 DB 트랜잭션 한계를 보일 때.

## 2026-11-21 — 집계를 원자적으로 갱신한 뒤 movement를 기록

- **결정:** 입고·출고는 먼저 조건부 원자 UPDATE로 `stocks.quantity`를 검증·갱신한 뒤 `stock_movements`를 INSERT한다. 전체 작업을 한 트랜잭션으로 묶는다.
- **배경 및 문제:** 출고 시 재고가 음수가 되지 않아야 하며, 현재 수량과 변경 이력이 항상 함께 커밋되어야 한다.
- **고려한 대안:** movement를 먼저 INSERT한 뒤 집계를 갱신한다. 명시적 `SELECT ... FOR UPDATE`로 읽고 잠근 뒤 수량을 갱신한다.
- **선택 이유:** 조건부 UPDATE 자체가 재고 허용 여부를 원자적으로 판단한다. UPDATE가 성공한 경우에만 movement를 기록하고, INSERT가 실패하면 트랜잭션 롤백으로 집계도 되돌린다. 별도 명시 잠금 쿼리는 추가하지 않는다.
- **단점 및 한계:** PostgreSQL은 같은 재고 행의 동시 UPDATE를 내부적으로 직렬화하므로 해당 행에 대한 요청은 순차 처리될 수 있다.
- **재검토 조건:** 동시성 통합 테스트나 실제 부하 측정에서 처리량 문제가 확인될 때.

## 2026-11-21 — 입고 중 상품 자동 등록과 후속 메타데이터 보정

- **결정:** 미등록 SKU 입고를 404로 거절하지 않는다. 상품명은 nullable로 두고 최소 식별 정보로 상품 등록과 입고를 완료한다. 자동 등록 상품의 `review_status`는 `NEEDS_REVIEW`, 사람이 정보를 보완하고 확인하면 `REVIEWED`로 관리한다.
- **배경 및 문제:** 현장 입고 작업은 가능한 한 중단 없이 진행되어야 하고, 상품명·특징·가격 등 메타데이터가 모두 준비되지 않았을 수 있다.
- **고려한 대안:** 모든 상품 정보를 받을 때까지 입고를 차단한다. SKU를 임시 이름으로 저장한다. 이름의 null 여부만으로 보정 대상을 판단한다.
- **선택 이유:** 현장 처리를 유지하고 모르는 정보는 null로 표현한다. 이름이 있어도 확인이 필요한 상품을 별도 상태로 관리한다. 상품 정보 보완은 재고 변경과 분리한다.
- **단점 및 한계:** 조회 응답에서 nullable 이름을 처리해야 하며 확인 상태를 관리해야 한다. 상태만으로 조회 성능을 보장할 수 없어 실제 조회 조건에 맞춰 인덱스를 검토해야 한다.
- **재검토 조건:** Phase 1 데이터 모델 및 실제 조회 실행 계획을 검토할 때. 후속 보정 API는 핵심 요구사항 완료 후 설계한다.

## 2026-11-21 — 변동 사유는 선택 입력을 기본으로 하고 조정·보정에는 필수

- **결정:** 모든 movement가 `reason`을 받을 수 있게 한다. 정상 입고·출고는 선택, 외부 조정·시스템 수량 변경·오입고 및 오출고 보정은 필수로 받는다.
- **배경 및 문제:** 정상 현장 처리는 간단히 유지하면서 비정상 수량 변경의 근거를 추적해야 한다.
- **고려한 대안:** 모든 movement에 사유를 강제한다. 모든 사유를 선택으로 두거나 조정에서만 사유를 저장한다.
- **선택 이유:** 정상 입출고의 입력 부담을 줄이고 필요한 경우에는 설명을 남긴다. 조정·보정은 사유 없이 확정되지 않도록 한다.
- **단점 및 한계:** 변경 상황에 따라 사유 필수 여부를 검증해야 한다. 미입고·미출고 등의 미처리 업무 상태는 movement 사유만으로 관리할 수 없다.
- **재검토 조건:** 조정 API의 구체적인 변경 유형과 외부 연동 계약을 설계할 때.

## 2026-11-21 — Tenant 인증은 초기 범위 밖

- **결정:** 고객사별 상품 구분과 데이터 격리를 데이터 설계에 고려하되, 인증되지 않은 임의 `tenant_id` 헤더를 보안 경계로 사용하지 않는다.
- **배경 및 문제:** 테넌트 데이터 분리가 필요하지만 인증 시스템이 없는 MVP에서 요청자가 보낸 헤더를 신뢰할 수 없다.
- **고려한 대안:** tenant 헤더만으로 요청을 격리하거나, 인증과 Tenant 기능까지 초기 환경 설정에 포함한다.
- **선택 이유:** 초기 구현 범위를 핵심 재고 기능에 한정하면서 거짓 보안 경계를 만들지 않는다.
- **단점 및 한계:** 인증 및 실제 Tenant 격리는 초기에는 제공되지 않는다.
- **재검토 조건:** 인증 및 권한 부여 설계가 시작될 때.
