# 개발 Workflow

## 원칙

테이블 세 개의 전체 설계를 먼저 검토하되, 전체 API를 한꺼번에 구현하지 않습니다. 도메인 단위 Vertical Slice로 한 번에 하나의 목표를 끝내고 리뷰합니다. 쉬운 설계를 우선하고 요구되지 않은 확장 구조를 만들지 않습니다. 설계 선택이 열려 있거나 요구 해석이 여러 가지면 구현 전에 사용자와 확인합니다.

각 Slice는 요구사항과 완료 조건 확인, 도메인 모델 및 필요한 DDL 검토, Repository·Service·Controller·DTO 구현, 테스트, PostgreSQL 통합 검증, 자체 리뷰, 필요한 문서 업데이트 순서로 진행합니다. 레이어는 실제 요구에 필요한 만큼만 추가합니다.

## 개발 순서

### Phase 0 — 초기 환경

Gradle/Spring Boot 실행 기반, PostgreSQL Docker Compose, Flyway, JUnit 5·Testcontainers, 문서와 협업 규칙을 구성합니다. 재고 API와 최초 DDL은 만들지 않습니다.

### Phase 1 — 데이터 모델

`items`, `stocks`, `stock_movements` 계약과 SKU·Tenant 키 범위, 무결성 제약을 검토하고 Flyway 최초 migration을 작성합니다. migration에는 정확히 세 테이블만 둡니다.

### Phase 2 — 상품 및 입고

상품 입고 API를 구현합니다. 미등록 SKU는 404 처리하지 않고 최소 식별 정보로 상품을 등록한 뒤 입고합니다. 기존 상품 재고 증가, movement INSERT, 동일 SKU 동시 최초 입고 중복 방지를 PostgreSQL 통합 테스트로 확인합니다. 부가 메타데이터 입력 없이도 입고가 완료되어야 합니다.

### Phase 3 — 출고

출고 API에서 미등록 상품과 재고 부족을 처리하고, 원자적 조건부 UPDATE로 음수 수량을 막습니다. 정상·재고 부족·동일 상품 동시 출고 테스트를 작성합니다.

### Phase 4 — 현재 재고 조회

상품 ID 기준 조회 API가 `id`, `name`, `quantity`를 반환하도록 구현하고 미등록 상품 404 및 movement 합계와 현재고 정합성을 검증합니다.

### Phase 5 — 안정성 개선

요청 ID 멱등성, 내용이 다른 중복 요청의 409, Tenant 데이터 범위, 오류 응답과 movement INSERT 실패 시 전체 롤백을 검토·검증합니다. 인증 시스템과 상품 보정 API는 필수 MVP 이후의 별도 검토 대상으로 둡니다.

### Phase 6 — 최종 검토

전체 PostgreSQL 테스트와 Compose 실행, README API 명세·실행 방법, 코드·보안·Git diff를 리뷰합니다. 릴리스 태그는 사용자 승인 후 별도 검토합니다.

각 Phase는 독립된 리뷰 단위입니다. 테스트가 통과하고 사용자가 리뷰하기 전에는 작업을 DONE으로 처리하거나 다음 Phase를 완료한 것으로 보지 않습니다.

## Git 흐름

현재 프로젝트는 `main`에서 작업합니다. 변경은 논리적 단위별로 나누며, 커밋은 `feature: 한글 변경 요약` 제목 뒤 빈 줄을 두고 중요한 변경점과 이유를 본문에 적습니다. 사용자가 변경을 승인하기 전에는 staging, commit, push를 하지 않습니다. push에는 별도 명시 승인이 필요합니다.

작업 하나의 검증을 마치면 승인 범위에서 커밋·푸시하고, 다음 작업의 목표와 설계는 사용자와 검토합니다. 사용자가 현재 작업의 푸시와 다음 단계 진행을 함께 승인하면 해당 범위에서 이어갑니다. 독립적인 여러 작업을 한꺼번에 모아 커밋하지 않습니다.
